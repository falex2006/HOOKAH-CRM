# Правила агентов Territory CRM

## Оркестрация задач

Основной Codex — координатор задачи. Для каждой содержательной задачи он сам выбирает подходящие роли из `.codex/team/team.json` и `.codex/team/roles/`, проходит этапы из `docs/AI_TEAM_WORKFLOW.md`, сводит результаты, реализует безопасные изменения и выполняет QA. Следуйте исполняемому регламенту `docs/AI_ORCHESTRATOR.md`. Не просите пользователя запускать роли вручную и не посылайте промежуточные уведомления о рутинном ходе работы.

Если доступны нативные инструменты субагентов Codex, делегируйте независимые исследования и проверки с чёткими границами. Одновременно запускайте не более трёх. Сначала запускайте безопасные независимые аудиты; не поручайте нескольким агентам одновременно изменять одни и те же файлы. Для каждой задачи, меняющей программный код, подключайте `code_health_engineer` к проверке исходного состояния и итогового diff; для чисто текстовых правок выбирайте его по необходимости. Для любых изменений бокового меню, маршрутов или верхней панели обязательным владельцем контракта является `system_architect`; design lead, frontend и QA подтверждают визуальную и функциональную стороны. Координатор отвечает за интеграцию, устранение конфликтов, итоговую проверку и отчёт. Профили ролей задают область работы и не являются технической песочницей или отдельными правами доступа.

В обычных обратимых локальных задачах действуйте без промежуточного согласования: исследуйте первопричину, внесите минимальную законченную правку, запустите относящиеся проверки, исправьте регрессии и запишите результат в рабочий журнал. Не останавливайтесь на отчёте, если безопасное исправление входит в запрос.

Перед работой читайте только документы, относящиеся к задаче: `docs/AI_TEAM.md` и `docs/AI_TEAM_WORKFLOW.md` — для командного процесса; `SITE_TREE.md` — для навигации; `DEVELOPMENT_WORKFLOW.md` — для пакетов и публикации; профиль из `.codex/team/roles/` — для подключаемой роли. Для изменений БД, безопасности, дизайна или релиза дополнительно применяйте соответствующие правила проекта.

Работайте только в заявленной области, сначала найдите первопричину, сохраняйте совместимость tenant/role/route, добавляйте проверку для исправленного сценария и фиксируйте результат. Не публикуйте production и не выполняйте необратимые операции без прохождения общего workflow.

Пользователь не хочет рутинных вопросов и промежуточных уведомлений. Не задавайте их для обычных решений, которые можно безопасно проверить локально. Это предпочтение не отменяет обязательные проверки, запрет на разрушительные операции или технические релизные условия. Если работа требует действия за этими границами, подготовьте всё безопасное и сообщите только конкретный блокер и необходимое решение.
