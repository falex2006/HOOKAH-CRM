# Оркестратор Territory CRM

## Решение

Проекту нужен координатор изменений, потому что одна функция CRM часто затрагивает бизнес-правила, интерфейс, API, права, базу данных и визуальную проверку. Отдельный постоянно работающий сервер агентов для этого не нужен: текущий Codex уже предоставляет основной задаче инструменты для запуска и контроля субагентов. В проекте основной Codex является оркестратором, а роли из `.codex/team/roles/` — его профильными инструкциями.

Это не фоновый сервис: он работает, пока активна задача Codex. Он не продолжает изменять репозиторий между задачами и не обещает автономную публикацию. Если нативное делегирование недоступно, основной Codex выполняет те же этапы последовательно.

## Рабочий цикл

1. Определить пользовательскую цель, затронутые страницы и завершённый сценарий. Прочитать только применимые требования и роль.
2. Проверить текущее состояние проекта, грязное рабочее дерево и связанные UI/API/БД контракты. Не перезаписывать чужие незавершённые изменения.
3. Сначала делегировать до трёх независимых задач: например, аудит API, UX-аудит или проверку безопасности. Для каждого изменения программного кода обязательно привлекать `code_health_engineer` для проверки исходного состояния и итогового diff. Агент получает конкретный вопрос, список допустимых файлов и формат результата. Совместное редактирование одних файлов не запускать.
4. Системному архитектору поручать сквозную связку «страница и действие → маршрут и метод → поля запроса/ответа → роль → состояния UI → сохранение → повторное чтение» и сохранять за ним владение боковой навигацией и верхней панелью на всех основных маршрутах. Backend, frontend и доменные роли подтверждают свои части.
5. Координатор сводит выводы, разрешает противоречия, выбирает минимальный безопасный пакет и реализует/интегрирует правки. Для спорного решения фиксирует основание в `docs/ai-team/DECISIONS.md`.
6. После изменений выполнить релевантные проверки: синтаксис и контракты, полный пользовательский путь, роли и ошибки, адаптивность и визуальное состояние. Инженер качества кода повторно проверяет diff, QA — итоговую интеграцию; нужные security/domain роли подключаются по затронутой области.
7. Обновить `docs/ai-team/WORK_LOG.md`: причина, изменение, затронутые файлы, миграции/API, команды проверки, результат и оставшиеся блокеры.
8. Release-менеджер проверяет diff и пакетный workflow. Публикация допускается только после всех проектных условий и проверок.

## Автономность и ограничения

- Обычные обратимые локальные правки, тесты и документация выполняются без остановок и рутинных вопросов пользователю.
- Успешный локальный тест не считается доказательством production-состояния.
- Не обходить auth, безопасность, правила миграций, проверки деплоя или firewall ради автоматизации.
- Не удалять production-данные и не выполнять необратимые операции без предусмотренного workflow и явного подтверждения.
- Не публиковать незавершённый пакет. Следовать `DEVELOPMENT_WORKFLOW.md`, включая счётчик и единый релизный gate.
- Если нет доступных субагентов, не изображать их результаты: пройти этапы самому и отметить фактически выполненные проверки.
- Пользователю сообщать итог по завершении работы или конкретный внешний блокер; не отправлять сообщения о каждом рутинном шаге.

## Текущая реализация

Оркестрация выполняется текущей задачей Codex через нативные субагенты, если этот runtime их предоставляет. `team.json` и профили помогают выбирать роли; `.github/workflows/ai-team-contracts.yml` проверяет их состав и обязательные правила, но не может подтвердить, что роль действительно запускалась в каждой задаче. Эти файлы не запускают агентов сами по себе и не дают профилям изолированных системных разрешений. Поэтому обязательное участие роли обеспечивается инструкциями координатору в `AGENTS.md` и этим workflow, а не отдельным техническим запретом на пропуск. Отдельный Agents API/SDK runtime потребовал бы отдельного приложения, API-учётных данных, бюджета, размещения и поддержки; сейчас он добавил бы инфраструктуру без необходимости.
