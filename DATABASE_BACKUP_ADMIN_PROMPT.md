# Промт: резервные копии базы данных заведения в админке HOOKAH POS

> **Режим работы:** спроектировать и подготовить предложение. Не менять код, БД, API, меню, конфигурацию сервера и production. Реализацию начинать только после отдельной прямой команды пользователя.

## Готовый промт для будущей разработки

Ты работаешь над HOOKAH POS. Нужно спроектировать и затем, только после явной команды пользователя на внедрение, реализовать безопасное управление резервными копиями данных заведения из панели администратора.

### Цель

Администратор заведения должен видеть состояние автоматических резервных копий всей базы и понимать, когда последняя копия успешно создана и проверена. Система должна автоматически и регулярно сохранять полную PostgreSQL-базу, а также позволять администратору вручную создать переносимую копию данных своего заведения, скачать её, позже загрузить файл обратно, проверить и восстановить данные. Он также должен уметь удалить выбранный пользовательский файл копии из хранилища в рамках политики хранения. История операций должна показывать автоматическое и ручное создание, проверку, загрузку, восстановление и удаление. Восстановление и удаление — отдельные опасные операции с защитой от случайного запуска. Решение должно учитывать текущую архитектуру проекта, существующую PostgreSQL-инфраструктуру и границы между заведениями.

Под «всей базой заведения» в интерфейсе понимай все бизнес-данные и настройки текущего tenant/venue, относящиеся к заведению и нужные для его восстановления. Не обещай экспорт всей физической PostgreSQL базы, системных пользователей, секретов, токенов, сессий или данных других заведений. До реализации проверь реальную схему и связи. Явно определи, какие сущности включаются, какие исключаются и почему. Если полная tenant-изоляция экспорта не может быть гарантирована, не предоставляй пользователю такой экспорт: предложи и реализуй только безопасный серверный backup всего PostgreSQL-кластера для операторов, либо вынеси безопасный tenant export в отдельное проектное решение.

### Контекст проекта, который нужно проверить заново

- Админ-панель: `/admin`, внутренний шаблон `admin.html`; центр настроек — `/admin#settings`.
- Список админ-маршрутов и ролей ведётся в `SITE_TREE.md`, `SITE_MAP.md`, `site-map.json`.
- Текущий интерфейс подключён через `portal.js` и общий `header-shell.js`; боковая навигация/верхняя панель принадлежат системному архитектору.
- Текущая серверная БД — PostgreSQL. Репозиторий уже содержит `backup-postgres.sh`, `verify-backup.sh`, `deploy-vps.sh` и описание в `DEPLOYMENT.md`. Существующий backup — серверный полный дамп PostgreSQL, закрытый правами на файлы и проверяемый gzip; он предназначен для эксплуатации/деплоя, а не является автоматически безопасным экспортом одного заведения.
- Серверные права должны проверяться на каждом API-запросе. Уже существуют роли owner/admin/manager и разрешение `settings`; фактические правила необходимо подтвердить по текущему коду и не расширять менеджеру право на выгрузку без обоснования.
- Используй актуальные исходники и миграции. Не доверяй старым отчётам как доказательству текущего production-состояния.

### Предварительное продуктовое решение

1. Разместить возможность как карточку **«Резервные копии»** в центре `/admin#settings`, рядом с настройками заведения/безопасности/журналом аудита. Если анализ навигации покажет, что ей нужен отдельный крупный экран, сначала предложить канонический маршрут и обновление дерева сайта; не добавлять пункт меню самостоятельно.
2. Два разных механизма обязательны и должны быть объяснены в UI: (а) автоматическая полная серверная копия PostgreSQL по расписанию для аварийного восстановления всей базы; (б) ручной переносимый файл текущего заведения для скачивания/загрузки через админку, если tenant-экспорт безопасен. Второй механизм не заменяет первый.
3. Основной пользовательский сценарий пользовательского файла — создать копию, скачать файл на устройство, при необходимости позже выбрать этот файл для загрузки и восстановить данные. В интерфейсе ясно указывать дату и время с часовым поясом заведения, размер, статус, формат, версию формата и охват данных. Для автоматических полных копий показывать время последнего успеха, результат проверки, расписание/частоту, срок хранения и статус здоровья без раскрытия полного дампа владельцу заведения.
4. Автоматизация выполняется на сервере по надёжному расписанию/планировщику, а не в браузере и не только пока администратор держит страницу открытой. Использовать текущий механизм `backup-postgres.sh`/его преемника после проверки пригодности; не запускать shell произвольными параметрами из HTTP. Поддерживать сериализацию задач, атомарное завершение, gzip/форматную проверку, мониторинг свободного места, журналирование результата и оповещение ответственного при пропуске/ошибке.
5. Определить RPO/RTO с учётом максимальной допустимой потери свежих данных и времени восстановления. Предложить разумную стартовую частоту и retention, но сверить с объёмом БД, нагрузкой, диском, стоимостью и ожиданиями пользователя до включения production расписания. Нужна защита от незаметного прекращения backup-задач и проверка восстановления по расписанию.
6. Сначала оценить надёжное серверное хранение, объём диска, срок хранения, права доступа, шифрование, резервирование самих копий и эксплуатационные оповещения. Автоматическое внешнее/облачное хранилище не настраивать без отдельного решения; если оно понадобится — хранить конфигурацию и секреты вне репозитория.
4. Восстановление не запускать из обычного списка одним нажатием. Для tenant-экспорта оно допустимо только если восстановление одной точки атомарно, проверено на реальной копии и не затрагивает другие tenant-данные. Для полного серверного pg_dump восстановление оставь операторской процедурой, пока не спроектированы изоляция, атомарность и отдельная безопасность. Для восстановления из загруженного файла сначала выполнить проверку формата, подписи/контрольной суммы, версии и принадлежности к заведению, затем показать сводку и отдельное подтверждение. Перед заменой данных обязательно создать и проверить pre-restore копию текущего состояния.
5. Удаление файла доступно только для копий текущего заведения, требует подтверждения с названием/датой файла и не удаляет единственную последнюю проверенную копию без дополнительного предупреждения/правила. После удаления файл должен стать недоступен немедленно, а операция — попасть в аудит. Уточнить политику удаления из локальных, временных и внешних хранилищ.

### Что исследовать до предложения реализации

- Текущие роли, разрешения и middleware авторизации; правила owner/admin/manager и tenant-контекст запроса.
- Все таблицы и зависимости, необходимые для восстановления заведения: пользователи/персонал, настройки, каталог/склад, заказы, оплаты/финансы, гости, бронирования, смены, аудит и интеграции. Не копировать секреты и активные сессии автоматически.
- Существующие ID, внешние ключи, tenant-scoping, миграции, удалённые/архивные сущности, файлы и вложения. Отдельно выяснить, где живут загруженные файлы, так как PostgreSQL backup сам по себе их не сохраняет.
- Как `backup-postgres.sh` вызывается из deploy и какие каталоги/права/сроки хранения установлены. Не связывать запрос администратора с deploy-скриптом и не давать HTTP-процессу произвольный запуск shell-команд.
- API routing, ограничения размера JSON, аудит действий, ограничения по времени/нагрузке и доступную файловую/объектную инфраструктуру.
- Текущие UI-настройки, визуальные правила, мобильную навигацию и поведение админки.

### Предлагаемый UX

Спроектируй интерфейс как центр управления сохранностью данных, а не набор технических кнопок. С первого взгляда администратор должен понимать: база сейчас защищена или есть проблема, когда прошла последняя успешная копия, какие данные охвачены, и что произойдёт при восстановлении.

#### Верхняя сводка состояния

- Заголовок **«Резервные копии»** с коротким спокойным пояснением: «Автоматические копии защищают всю базу. Файл заведения можно сохранить у себя и использовать для переноса или восстановления».
- Статусная карточка со значком и цветом, но всегда и с текстовой меткой: **«Защита работает»**, **«Создаётся копия»**, **«Нужна проверка»**, **«Есть проблема»**. Не полагаться только на цвет.
- Показывать «Последняя успешная копия», её дату/время в часовом поясе заведения, размер и «Проверена восстановлением: …». Отдельно показывать «Следующая копия: …» только если расписание реально подтверждено инфраструктурой.
- Для финансов визуально сделать приоритет понятным: отдельная строка **«Финансы, оплаты и смены»** со статусом покрытия в последней проверенной копии. Рядом аналогично показать **«Гости и история»**, **«Товары и склад»**, затем «Остальные данные». Статус означает результат проверки восстановленной копии, а не эвристическую оценку.
- При аварийной просрочке/ошибке показать заметный текст, дату последней пригодной копии и следующее безопасное действие/контакт. Не показывать технический stack trace, пути сервера или секреты.

#### Автоматические копии всей базы

- Отдельная карточка **«Автоматическая копия всей базы»** со статусом планировщика, последним успехом, последней проверкой восстановления, расписанием и retention. Пояснить простыми словами, что это полный серверный backup и из интерфейса владельца нельзя скачивать общий дамп.
- Администратору заведения дать read-only информацию о здоровье механизма; не предлагать менять технический cron/серверные пути/ключи из CRM.
- Раскрываемые детали для доверенного оператора могут показывать задания/ошибки без содержимого данных. Не смешивать операторские функции с обычными правами администратора заведения.

#### Ручное сохранение файла заведения

- Отдельная карточка **«Копия этого заведения»** с основной кнопкой **«Создать копию»** и вторичной ссылкой **«Загрузить файл копии»**.
- Перед созданием компактный диалог объясняет: что войдёт, что исключено, где временно хранится файл, срок доступности и можно ли потом восстановить его на этой/другой точке. Кнопки: **«Создать копию»** и **«Отмена»**.
- После старта показать неблокирующее состояние «Создаём копию…», индикатор выполнения только если backend способен достоверно сообщить прогресс; иначе показывать этапы без выдуманного процента: «Подготовка → Формирование → Проверка». Кнопку повторного запуска блокировать до завершения.
- По успеху показать «Копия готова», время, размер и проверку целостности; доступные действия — **«Скачать файл»**, **«Понятно»**. После обновления страницы запись остаётся в истории.
- Ошибка должна объяснять восстановимое действие («Не удалось создать копию. Данные не изменены. Повторите позже или обратитесь к администратору системы»), сохранить безопасный код операции и дать **«Повторить»** при допустимости.
- Историю визуально разделить на «На сервере» и «Загруженные файлы/импорт», если это упрощает понимание. На строке показывать дату, источник, размер, версию, scope, результат проверки и меню действий. Не делать таблицу шире мобильного экрана.

#### Загрузка и восстановление

- Загрузка начинается явным действием **«Загрузить файл копии»**. Покажи допустимые форматы, максимальный размер и предупреждение: загрузка и проверка сами по себе базу не меняют.
- После выбора файла показывать имя, размер и этапы **«Загрузка → Проверка файла → Готов к восстановлению»**. Предусмотреть отмену загрузки до начала восстановления и безопасную очистку временного файла.
- Если файл не проходит проверку, показать короткую причину (например, «Файл повреждён», «Формат не поддерживается», «Копия принадлежит другому заведению», «Файл создан для несовместимой версии») и гарантировать видимым текстом, что текущие данные не менялись.
- После проверки показать экран **«Проверка копии»** с метаданными: дата создания, исходное заведение, формат/версия, размер, охват, целостность и совместимость. Персональные данные из архива в preview не показывать.
- До восстановления показать отдельный экран/диалог **«Восстановить данные?»**: явное название целевого заведения, дата копии и понятное резюме затрагиваемых разделов. Предупреждение коротко и конкретно: текущие данные будут заменены/изменены согласно выбранной стратегии; новые записи после даты копии могут быть потеряны. Указать, что система сначала создаст защитную копию текущего состояния.
- Требовать повторное подтверждение, например ввод короткой фразы **«ВОССТАНОВИТЬ»** или повторную аутентификацию — выбрать один UX-механизм по модели угроз, не ставить два раздражающих барьера без причины. Кнопки назвать однозначно: **«Восстановить данные заведения»** и **«Отмена»**; опасная кнопка визуально отличается, но остаётся доступной и читаемой.
- Долгое восстановление выполнять асинхронно. Показывать шаги без ложного процента: «Проверяем копию → Сохраняем текущее состояние → Восстанавливаем данные → Проверяем результат». Пока идёт критическая операция, явно сообщить, можно ли закрыть страницу и как вернуться к статусу; запретить запуск второй операции.
- Успех: экран **«Восстановление завершено»**, дата копии, список успешно сверенных групп (финансы, гости, товары/склад и др.), ссылка **«Открыть CRM»** и подсказка, если потребуется повторный вход. Перед возвращением в CRM заново загрузить данные/контекст и инвалидировать устаревшие клиентские кэши.
- Частичный/неуспешный результат не маркировать как успех. Показать **«Восстановление не завершено»**, были ли данные откатаны к pre-restore snapshot, текущую доступность CRM и конкретный дальнейший шаг. Не скрывать ситуацию за toast.

#### Риски восстановления: показать до подтверждения

До последнего подтверждения явно и простыми словами перечислить последствия конкретно выбранной стратегии восстановления. Не ограничиваться общей фразой «операция опасна».

- **Потеря новых изменений:** записи, созданные после даты копии, могут быть удалены или заменены. Привести дату копии и предупредить, что более новые финансовые операции, гости/история, заказы, складские движения, брони и настройки могут пропасть, если стратегия их перезаписывает.
- **Финансовые расхождения:** восстановление старых оплат, возвратов, расходов, зарплат и закрытий смен может не совпасть с фактическими кассой/эквайрингом/отчётами. Не обещать автоматически «свести» внешние платежи; показать период, который будет затронут, и требование сверки после восстановления.
- **Дубли и связи:** смешивание копии с текущими строками вместо полной замены может создать дубликаты или осиротевшие связи; заранее определить режим (полная замена tenant или поддерживаемое слияние) и не давать пользователю выбирать технически небезопасный режим.
- **Совместимость версии:** старая/новая схема приложения может не принять файл или изменить смысл полей. Проверка должна выявить неподдерживаемую версию до изменения данных; не запускать частичный импорт с молчаливым пропуском таблиц.
- **Временная недоступность:** во время восстановления операции CRM могут быть остановлены, заблокированы или видеть устаревший кэш. Показать ожидаемый режим обслуживания и запретить конфликтующие записи/операции до окончания проверки.
- **Сессии и доступ:** после восстановления могли измениться персонал, разрешения и пользовательские данные. Завершить/обновить активные сессии безопасным способом и потребовать повторный вход, если это необходимо; не восстанавливать старые секреты и токены без отдельного обоснования.
- **Файлы вне БД:** фотографии, документы, вложения или иные объекты могут не входить в PostgreSQL-копию. Показать, входят ли они в выбранный backup-набор; не утверждать, что восстановление полное, если связанный файловый слой не сохранён.
- **Ошибка в середине операции:** до начала обязателен проверенный pre-restore backup. Система должна иметь технически доказанный откат; в диалоге описать, что произойдёт при неудаче, а итоговый экран сообщит, сохранились ли исходные данные или был выполнен rollback.
- **Необратимое production-действие:** никогда не использовать production для QA-проверки destructive restore. Для реальной боевой операции до подтверждения показать конкретное заведение и дату, потребовать предусмотренное дополнительное подтверждение, записать аудит и использовать maintenance/lock на время восстановления.

Сделай краткий preview до действия: **цель восстановления**, **дата копии**, **стратегия (замена/иная явно описанная операция)**, **разделы и период под риском**, **наличие свежей защитной копии**, **ожидаемая недоступность**, **действие при ошибке**. Если хотя бы один критичный пункт неизвестен, кнопку восстановления не активировать и объяснить причину.

#### Удаление файла

- Действие **«Удалить копию»** находится в меню строки, отдельно от восстановления и скачивания.
- Диалог подтверждения называет точную копию по дате/размеру и уточняет последствия: файл в серверном хранилище будет удалён и больше не сможет использоваться для восстановления. Для сохранённого на устройстве файла пояснить, что удаление серверной записи не удаляет уже скачанную локальную копию.
- Если это последняя пригодная копия, по умолчанию запретить удаление либо потребовать сначала создать/проверить другую копию; выбранное правило должно быть одинаково в UI и API.
- После удаления обновить историю и показать краткое подтверждение; при ошибке сохранить запись и предложить повторить. Не удалять файл до прохождения подтверждения.

#### Риски удаления: показать до подтверждения

- **Утрата возможности восстановления:** удалённый архив больше нельзя использовать для возврата к его состоянию. Диалог должен назвать конкретный файл/дату и прямо сказать, что восстановление из него станет невозможно.
- **Удаление последней пригодной копии:** по умолчанию блокировать удаление последней проверенной копии. Если продукт допускает исключение, требовать сначала создать и проверить замену; одного предупреждения недостаточно.
- **Удаление не отменяет уже скачанные экземпляры:** объяснить, что действие удалит серверный файл/запись хранения, но не копии на компьютере пользователя или внешнем носителе; эти копии могут сохранять чувствительные данные и должны храниться безопасно.
- **Влияние на автокопии/retention:** явно отделить пользовательские файлы заведения от автоматических полных серверных backup. Администратор заведения не должен случайно удалить общий backup; ручное удаление не меняет расписание и retention.
- **Юридический/аудиторский след:** удалить содержимое файла по политике, но оставить минимальную audit-запись события без самого содержимого, токенов и персональных данных. Уточнить поведение версий/реплик/объектного хранилища и срок фактического физического удаления.
- **Ошибка или задержка удаления:** не убирать копию из списка и не показывать успех, пока backend не подтвердил требуемый статус удаления. Если удаление асинхронное или есть задержка удаления версий, показать соответствующее состояние.

В диалоге удаления показать название/дату/размер, причину удаления, наличие другой проверенной копии и точный эффект на серверное хранение. Основные кнопки: **«Удалить эту копию»** и **«Оставить копию»**; избегать неоднозначного «Да/Нет».

#### Общие состояния и адаптивность

- Обязательные состояния каждого блока: начальная загрузка/skeleton, пустое, успешное, выполняется, ошибка чтения, ошибка действия, нет доступа, устаревшая копия, offline/нет связи и повторная попытка.
- Поддержать клавиатуру, screen reader (статусы через live region), фокус в подтверждающих диалогах и возврат фокуса после закрытия. На телефонах/Fold кнопки и строки складываются вертикально; опасные действия не должны быть рядом с основной кнопкой без меню/разделения.
- Не сообщать «всё сохранено» только потому, что файл создан: использовать точные статусы «создан», «проверен», «восстановление проверено» с датами и источником доказательства.

Карточка или экран «Резервные копии» содержит:
- Короткое пояснение, что сохраняется и что не входит в копию.
- Статус последней операции: «Готово», «Выполняется», «Ошибка», время, длительность и понятное следующее действие.
- Кнопку **«Создать копию»** с защитой от повторного запуска, подтверждением перед стартом и понятным состоянием ожидания. Длительную задачу выполнять асинхронно, с серверным статусом, а не удерживать HTTP-запрос до завершения дампа.
- Историю доступных копий: дата/время в TZ заведения, охват, формат, размер, результат проверки целостности, срок хранения, действия «Скачать» и (только если отдельное решение допускает) «Восстановить».
- Пустое состояние до первой копии, ошибку загрузки списка, отсутствие свободного места/ошибку создания, истёкшую или недоступную копию и успешное скачивание.
- Небольшой экранный layout, доступность клавиатурой и touch-friendly элементы на телефонах/Fold/планшетах; без перегрузки общего меню.
- Загрузка файла копии с явными лимитами размера и допустимого формата, прогрессом, отменой до начала восстановления, проверкой до импорта и понятными ошибками. Проверка файла сама по себе не изменяет данные.
- Восстановление из уже сохранённой копии и из загруженного файла — отдельные сценарии. Перед подтверждением показать целевое заведение, дату/источник копии, ожидаемый scope и предупреждение, какие текущие данные будут заменены/обновлены.
- Удаление копии — отдельное действие в меню строки с подтверждением; после успеха обновить список и статус последней доступной копии.

### Предлагаемый технический контракт — подтвердить архитектором до реализации

Сначала выбери между двумя честно различными продуктами и зафиксируй решение:

**Вариант A — полный серверный backup PostgreSQL.** Он содержит все tenant-данные. Администратор может видеть статус и запрашивать копию, но скачивание такого архива владельцу заведения запрещено, если в нём могут быть чужие tenant-данные, учётные записи или секреты. Управление/скачивание остаётся только у доверенного оператора платформы по отдельному интерфейсу и политике.

**Вариант B — экспорт/backup только одного заведения.** Это отдельный формат, формируемый сервером по явному allowlist сущностей и проверенной схеме связей. У него есть версия формата, метаданные (`venueId`, время UTC, TZ, версия приложения/схемы, список включённых сущностей, контрольная сумма); исключены секреты, пароли, PIN, сессии, токены, конфигурация сервера и любые строки других tenant. Нельзя применять общий pg_dump к HTTP-скачиванию. Нужны лимиты размера/частоты, атомарное создание, временная ссылка/поток с коротким сроком действия, безопасное удаление временных файлов и отдельные тесты на межtenant-утечку.

В качестве стартового эскиза API (не считать утверждённым контрактом):

- `POST /api/venue-backups` — запросить создание копии текущего venue; сервер извлекает venue из авторизованной сессии, а не доверяет `venueId` клиента. Возврат `202` с `jobId`.
- `GET /api/venue-backups` — список только копий текущего venue, пагинация и статусы.
- `GET /api/venue-backups/jobs/:jobId` — статус задания с безопасной проверкой принадлежности.
- `GET /api/venue-backups/:backupId/download` — скачать только разрешённую копию текущего venue через авторизованную одноразовую/короткоживущую выдачу.
- `POST /api/venue-backups/upload` — принять файл в потоковом режиме с лимитом размера; сначала поместить в карантинное временное хранилище, не применять его к БД.
- `POST /api/venue-backups/:backupId/validate` и/или `POST /api/venue-backups/uploads/:uploadId/validate` — проверить формат, размер/структуру, контрольную сумму или цифровую подпись, версию схемы, допустимый scope и соответствие текущему venue; вернуть сводку без чувствительных данных.
- При утверждённом восстановлении — отдельная двухфазная операция: запросить план/подтверждение, затем запустить отдельную асинхронную задачу с дополнительной аутентификацией, серверной блокировкой, проверенной pre-restore копией и аудитом. Точный API не фиксировать до модели угроз и плана атомарности.
- `DELETE /api/venue-backups/:backupId` — удалить только принадлежащую текущему venue копию, с правилом защиты последней проверенной копии и аудитом. Удаление загруженного временного файла/карантинной записи описать отдельно.
- Не выставлять полную серверную копию через owner/admin API. Статус автоматических копий в пользовательском интерфейсе должен идти через безопасный read-only агрегат без путей, имён хостов, дампов, секретов и данных других заведений. Создание/ротация полного pg_dump остаётся серверной scheduler/job операцией под инфраструктурной учётной записью.

Для каждой операции архитектор обязан оформить таблицу: UI действие → HTTP метод/маршрут → поля и ответ → permission → tenant scope → состояния UI → изменение/файл на сервере → повторное чтение → QA.

### Требования безопасности и надёжности

- Проверять роль и право сервером для каждой операции; скрытие кнопки в UI не является защитой. Начальный вариант доступа — owner/admin текущего заведения; подтвердить проектную модель и минимальные разрешения. Manager и staff по умолчанию не получают право создавать/скачивать/восстанавливать копии.
- Жёстко привязывать каждый объект/задание к текущему venue; при подмене ID отвечать безопасным `404/403`, не раскрывая наличие чужой копии.
- Защищать скачивание от CSRF, IDOR, path traversal и утечки через логи/cache. Для архива выставлять безопасные `Content-Type`, `Content-Disposition`, `Cache-Control: no-store`; имена файлов не строить из непроверенного ввода.
- Считать дампы и экспорты чувствительными данными: шифрование при хранении и передаче, закрытые права доступа, отсутствие публичных static URL, контролируемое удаление по retention. Секреты шифрования хранить вне репозитория и самого архива.
- Для автоматической полной базы определить целевые RPO/RTO, частоту, retention и место хранения. Защитить резервные копии от отказа того же диска/сервера: оценить второй независимый носитель/регион или поддерживаемое объектное хранилище, шифрование до отправки и политику ключей. Автоматическую копию, лежащую только рядом с основной БД на том же диске, не считать достаточной аварийной защитой.
- Добавить наблюдаемость scheduler/job: последний запуск, успех/ошибка, длительность, размер, свободное место и дата последней успешной проверки восстановления. Просроченная копия/ошибка должна порождать сигнал ответственному; логи не содержат содержимое дампа или секреты.
- Приоритет сохранности: прежде всего финансовые записи и их связи (заказы, платежи, возвраты/расходы, зарплаты, смены/касса), затем гости и лояльность, каталог/товары, рецептуры/техкарты, остатки и движения; далее бронирования, персонал, настройки, задачи, аудит и остальные бизнес-таблицы. Для полного pg_dump физически сохраняется вся БД целиком; перечисление здесь задаёт обязательные проверки полноты и целостности, а не фильтрацию. Отдельно проверить файлы/вложения, если они хранятся вне PostgreSQL.
- Не помещать содержимое, URL скачивания, токены, SQL и персональные данные в audit/log. В аудит записывать actor, venue, действие, идентификатор копии/задания, timestamp, итог и безопасные метаданные.
- Вести операции как state machine: queued/running/validating/ready/failed/expired; идемпотентность или блокировка повторного клика; атомарная публикация только после завершения и проверки целостности. Ошибки очищают незавершённые временные файлы.
- Загрузка всегда сначала попадает в карантин. Не доверять расширению и MIME от клиента; проверять сигнатуру/структуру формата, контрольную сумму/подпись, размер распакованного содержимого и защиту от архивной бомбы/path traversal. Ограничить время, размер, число файлов и частоту.
- Перед восстановлением сверить venue ID/организацию, версию формата и схему, показать пользователю точное целевое заведение и план. Несовпадение владельца/venue блокирует операцию; не разрешать импорт файла одного заведения в другое без отдельной явно спроектированной миграции.
- Восстановление должно быть атомарным или иметь доказанный rollback: при любой ошибке исходные данные остаются целыми либо возвращаются из проверенной pre-restore копии. Защитить систему от параллельных изменений/операций и корректно обновить сессии после восстановления.
- Удаление файла — серверная операция по внутреннему идентификатору, никогда по переданному пути; обеспечить безопасное поведение при повторном запросе, аудит, очистку временных частей и сохранение настроенного retention.
- Составить и проверить процедуру создания, скачивания, загрузки, проверки, восстановления, удаления и истечения срока копии. Наличие файла без доказанного round-trip восстановления не считается работающей резервной копией.
- Проверять ограничение частоты, квоты хранилища и параллелизм; не истощать CPU, память, диск и соединения PostgreSQL.
- Составить и проверить процедуру восстановления. Наличие архивного файла без доказанного восстановления не считается работающей резервной копией.
- Разделить аудит действий администратора и инфраструктурные логи. Не писать в пользовательский журнал лишние чувствительные подробности.

### Критерии приёмки будущей реализации

- Owner/admin видит только данные и копии своего текущего заведения; manager/staff и другая точка не могут получить их через UI или прямой API.
- Успешное создание отражается в истории, статус переживает обновление страницы, а скачанный архив проходит проверку целостности и соответствует заявленному scope.
- Проверен полный round-trip: создать → скачать → загрузить файл обратно → валидировать без изменения БД → восстановить на disposable окружении → сверить ключевые сущности/связи и продолжить работу CRM. Повторить загрузку файла, скачанного ранее, чтобы доказать переносимость вне серверного хранилища.
- Удаление доступной копии требует подтверждения, удаляет только выбранный файл текущего venue, корректно обновляет историю, оставляет аудит и соблюдает правило последней проверенной копии. Проверены повторное удаление, неизвестный ID и чужой venue.
- UX проверен по скриншотам/ручному проходу для desktop, узкого телефона, Fold и планшета; подтверждены ясность названий, отсутствие ложного процента/статуса, корректный фокус и понятный dangerous-flow восстановления/удаления.
- Проверены испорченный, обрезанный, неверного формата, слишком большой, старой/будущей версии и принадлежащий другому заведению файл; ни один не меняет данные.
- Проверено фактическое включение важных доменных данных и исключение секретов/данных другой точки на синтетических fixture для нескольких tenant.
- Проверено, что автоматическое задание запускается по расписанию независимо от открытой админки, создаёт полную копию всей PostgreSQL-базы, сериализуется с другими backup/deploy задачами, не публикует неполный архив и подаёт сигнал при пропуске/ошибке/нехватке места.
- Автоматический полный backup проверен восстановлением в изолированную disposable PostgreSQL БД; сравнить финансовые суммы и число/связность критичных строк, гостей/истории, товаров/каталога, складских остатков/движений и других доменов. Убедиться, что восстановление копии целиком сохраняет связи и запускается на совместимой схеме приложения.
- Зафиксированы и согласованы целевые RPO/RTO, частота, срок хранения, место хранения и стоимость; подтверждено, что есть копия вне отказовой зоны основной БД и настроено оповещение о неудаче.
- Проверены дубликатный запрос, пустая база, большая копия, нехватка места, таймаут, недоступная БД, ошибка валидации, истечение срока и прерывание процесса.
- Восстановление выполняется только на disposable базе/tenant или изолированном QA-контуре: проверены атомарность, pre-restore snapshot, сохранность остальных заведений, повторный вход после восстановления и фактическая работа ключевых экранов. Запрещено тестировать destructive restore или удаление пользовательских копий на production.
- После внедрения выполнить все релевантные существующие проверки проекта и полный QA-флоу функции: синтаксис, `git diff --check`, QA-контракты, API/роль/tenant тесты, миграции при наличии, backup round-trip, ошибки/границы загрузки, доступность, адаптивность и визуальную проверку. Запустить проектный acceptance/smoke-набор, который применим к изменённым областям; зафиксировать точные команды и PASS/FAIL, исправить регрессии и повторить проверки. Не заявлять, что «прогнали всё», если часть полного набора недоступна; явно перечислить, что не запускалось и почему.
- UI/API/БД проходят полный сценарий, доступность и адаптивность; проверены канонический маршрут и копия в `dist/` при необходимости.
- Текущие серверные backup/deploy/retention контракты не сломаны. Отдельно проверена совместимость старых копий/версий экспортного формата.
- Проверены ротация и retention на тестовом каталоге: удаляются только копии старше политики, никогда не удаляется последняя пригодная копия, нет гонки между scheduler и deploy, незавершённые временные файлы очищаются.

## Краткое архитектурное направление

Рекомендуемое направление: раздел в центре настроек администратора показывает read-only здоровье автоматических полных копий всей PostgreSQL-базы (операторское создание по серверному расписанию, хранение вне отказовой зоны основной БД, retention, контроль восстановления и оповещения) и отдельно управляет пользовательскими копиями текущего заведения: создание, скачивание, загрузка, проверка, восстановление после явного подтверждения и удаление. Финансовые данные, гости и товарно-складская область — обязательные приоритеты контрольного восстановления. Все tenant-файловые операции возможны только после строгого доказательства изоляции и атомарности. Если безопасный tenant restore не получается обеспечить, не имитировать его; предложить безопасную границу продукта. Расписание, целевые RPO/RTO, retention и внешнее хранилище согласовать до включения на production.

## Проверенный контекст на момент подготовки

- `/admin#settings` — существующий центр настроек; отдельный пункт «Резервные копии» в текущей карте пока не описан.
- `backup-postgres.sh` сохраняет полный gzip PostgreSQL dump в серверный каталог, с `flock`, `umask 077`, проверкой gzip и ротацией по возрасту; `verify-backup.sh` выполняет проверочное восстановление в отдельную БД и удаляет её.
- `deploy-vps.sh` создаёт/переиспользует проверенную копию перед обновлением. Эти скрипты сами по себе не дают безопасного per-venue экспорта или пользовательского API скачивания.
- Текущий `backup-postgres.sh` создаёт копию при ручном вызове/деплое; проверка показала существование механизма доработки, но не подтвердила отдельный работающий регулярный scheduler. В этапе внедрения проверить фактическую инфраструктуру расписания, health/alerting и независимое хранилище.
- Настоящий scope таблиц, включая файлы и секреты, должен быть установлен в отдельном discovery перед кодом.

## Технические рекомендации и первичные источники

Используй эти официальные руководства как исходные требования при проектировании; перед внедрением проверь соответствие версии PostgreSQL и инструментов, реально используемых проектом.

- PostgreSQL описывает три разных стратегии: логический SQL dump, файловую копию и непрерывное архивирование WAL. Выбор зависит от RPO/RTO, размера и сложности эксплуатации; не считать один ежедневный `pg_dump` решением для point-in-time recovery: [PostgreSQL: Backup and Restore](https://www.postgresql.org/docs/current/backup.html).
- `pg_dump` создаёт согласованный snapshot при параллельной работе пользователей и выгружает одну БД. Он не сохраняет cluster-wide объекты — роли и tablespaces; для них PostgreSQL отдельно описывает `pg_dumpall`. Разделить и документировать копию данных CRM и инфраструктурные глобальные объекты, не выставляя последние владельцу заведения: [PostgreSQL: pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html), [PostgreSQL: pg_dumpall](https://www.postgresql.org/docs/current/app-pg-dumpall.html).
- Для малого/среднего текущего контура разумно оценить ежедневные base/logical backups как простой первый слой; если бизнесу нужна малая допустимая потеря операций или восстановление на момент до ошибки, исследовать WAL archiving + base backups и PITR. У PostgreSQL прямо указано, что PITR требует файлового base backup и WAL, а логический `pg_dump` для этого не подходит; это более сложная эксплуатационная схема, которую нужно проверить end-to-end: [PostgreSQL: Continuous Archiving and PITR](https://www.postgresql.org/docs/current/continuous-archiving.html).
- Проверка контрольной суммы/манифеста полезна, но не заменяет запуск тестового восстановления и проверку, что восстановленная БД действительно содержит ожидаемые данные и работает: [PostgreSQL: pg_verifybackup](https://www.postgresql.org/docs/current/app-pgverifybackup.html).
- Держать отдельную зашифрованную и по возможности offline/immutable копию вне сервера/диска основной БД; регулярно проверять доступность, целостность и процедуру аварийного восстановления. CISA отдельно предупреждает, что злоумышленники могут искать и удалять доступные сетевые копии: [CISA StopRansomware Guide](https://www.cisa.gov/stopransomware/ransomware-guide).
- Файл, загруженный через UI, принимать в карантин вне webroot; не доверять имени/MIME от браузера, ограничивать размер, проверять сигнатуру и распакованный объём, назначать внутреннее случайное имя и читать только через авторизованный handler. Эти меры следуют из [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) и [OWASP Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html).
- Цели восстановления определять через анализ влияния на бизнес, а не выбирать частоту «на глаз»: согласовать допустимую потерю данных (RPO), время возврата сервиса (RTO), приоритеты процессов и процедуру восстановления. Для рамки планирования см. [NIST SP 800-34 Rev. 1](https://csrc.nist.gov/pubs/sp/800/34/r1/upd1/final).

Практическое следствие для HOOKAH POS: начать discovery с текущего `pg_dump` и инфраструктурного расписания; не менять инструмент только ради моды. Сохранить совместимый логический backup, добавить устойчивый scheduler + off-host encrypted copy + мониторинг/оповещение + регулярный restore drill. Если согласованный RPO требует защиты изменений между полными копиями, отдельно спроектировать PITR с WAL, оценить объём/стоимость и автоматизировать проверяемое восстановление. Финансы, платежи, смены/касса, гости и склад/товары обязаны входить в контрольные QA сверки восстановленной полной базы.

### Готовые PostgreSQL-инструменты, которые нужно оценить до самописной реализации

Не писать собственный backup-движок, scheduler, WAL-архиватор или retention manager, пока не доказано, что зрелый инструмент не подходит. Перед выбором проверь актуальные версии, совместимость с нашей версией PostgreSQL/Docker и возможность установки/эксплуатации на VPS; не обновляй production и не устанавливай пакет в рамках этапа проектирования.

| Вариант | Что уже умеет | Когда рассматривать | Что остаётся HOOKAH POS |
|---|---|---|---|
| Текущие `pg_dump` + `backup-postgres.sh` | Простой согласованный logical dump одной БД, gzip, контроль целостности gzip, блокировка конкурентного запуска, закрытые права файла и проверочное восстановление в скрипте QA | Самый простой низкосложный базовый слой, если объём небольшой и согласованный RPO допускает интервал между полными копиями | Надёжное расписание, off-host копия, шифрование/ключи, мониторинг/оповещения, политика RPO/RTO и операторский UX |
| **pgBackRest** | PostgreSQL physical full/differential/incremental backups, WAL archive/PITR, retention, checksum/integrity, сжатие/параллелизм, шифрование репозитория, несколько локальных/удалённых хранилищ и S3-compatible варианты | Сильный кандидат для self-hosted PostgreSQL на VPS/Docker, если нужны штатные PITR, шифрованные удалённые репозитории и управляемый lifecycle | Подключение как инфраструктурного компонента, конфигурация/секреты, мониторинг/алерты, restore drills; отдельная CRM-страница для статуса и tenant-файлов |
| **WAL-G** | Физические base backups и WAL push/fetch, сжатие/шифрование, cloud/object storage, incremental-подходы и команды управления архивами | Рассматривать при уже принятом cloud/object-storage подходе, автоматизации через существующую инфраструктуру или требованиях использовать лёгкий утилитарный пайплайн | Развёртывание/обслуживание WAL archiving, retention, мониторинг/алерты, безопасная интеграция и UX; проверить статус поддержки конкретного backend/версии |
| **Barman** | Централизованное управление несколькими PostgreSQL-серверами/кластерами, base backup, WAL архивирование и PITR-восстановление | Рассматривать при переходе к отдельному серверу backup и централизованной эксплуатации нескольких инсталляций | Отдельный backup host/сервис, его HA/защита, интеграция статусов с CRM и tenant-файл-экспорт отдельно |

Предварительная рекомендация для текущего проекта: сначала провести короткий compatibility/ops аудит **pgBackRest** как вероятного кандидата для полной серверной автоматической защиты с WAL/PITR и удалённым репозиторием; оставить текущий `pg_dump`/restore путь как переносимый logical export или совместимый fallback, если это оправдано. WAL-G — сравнить, если объектное хранилище уже доступно/предпочтительно. Barman имеет смысл, если появляется отдельный централизованный backup host или несколько независимых PostgreSQL инсталляций. Это направление для проверки, не окончательное решение и не указание немедленно устанавливать инструмент.

Оценить для каждого кандидата: поддержку текущей версии PostgreSQL и Docker; операционную сложность на одной VPS; требования к WAL/replication slots и риски заполнения диска; шифрование и управление ключами; поддержку выбранного off-host storage; retention без удаления единственной рабочей цепочки; метрики и алерты; тестирование restore/PITR; миграцию и чтение уже имеющихся gzip SQL dumps; стоимость хранения/трафика; процедуру обновления самого backup-инструмента. Принести таблицу сравнения и проверяемый PoC в disposable среде до выбора.

Готовые инструменты защищают серверную базу, но не решают экспорт/восстановление **одного tenant** через CRM. Для этого остаётся отдельный версионированный tenant-пакет и отдельный безопасный import workflow; не выдавать полный backup tool repository или весь PostgreSQL cluster владельцу точки.
