# Workflow команды

## 1. Intake

Продуктовый аналитик фиксирует цель, пользователя, ограничения, критерии приёмки и затронутые страницы. Если задача неоднозначна, формулируется безопасное предположение и список вопросов.

## 2. Discovery

Архитектор строит карту зависимостей. Дизайн-лид и визуальный аудитор проверяют текущий экран. Backend/data/domain-роли ищут существующие API, таблицы, миграции и связанные цепочки.

## 3. Решение

Координатор выбирает минимальный пакет изменений. Для архитектуры, БД, ролей, финансов и чувствительных данных обязательны соответствующие согласующие роли. Спорное решение заносится в `docs/ai-team/DECISIONS.md`.

## 4. Реализация

Frontend, backend и data-инженер работают в своих границах. Дебаггер исправляет первопричину, а не маскирует симптом. Изменения одной цепочки проходят вместе: UI → API → БД → повторное отображение.

## 5. Проверка

QA проверяет happy path, пустую базу, ошибки, права ролей, повторное открытие и связанные маршруты. Визуальный аудитор проверяет desktop, мобильную ширину, Fold и планшет. Security проверяет RBAC, tenant isolation и чувствительные данные.

## 6. Release

Release-менеджер проверяет `git diff --check`, синтаксис, релевантные smoke-тесты, миграции, commit SHA и отчёт. После публикации повторяется health check и короткий production QA.

## Правила блокировки

- Нельзя менять БД без миграции и плана совместимости.
- Нельзя удалять данные без явного сценария, аудита и подтверждения.
- Нельзя менять визуальные правила отдельной страницы в обход `VISUAL_PAGE_RULES.md`.
- Нельзя считать функцию готовой, если есть только форма или API.
- Любой найденный дефект получает воспроизводимый сценарий и владельца.
