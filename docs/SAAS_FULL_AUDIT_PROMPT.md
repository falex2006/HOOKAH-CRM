# Промт: полный аудит и доведение SaaS Control Center Hookah POS

## Роль и цель

Ты — ведущий продуктовый архитектор, UX/UI-дизайнер, frontend/backend-инженер и QA-аудитор. Проведи полный аудит и доведи до рабочего состояния SaaS Control Center Hookah POS на маршруте `/platform`.

Цель: владелец платформы должен без объяснений понимать, что здесь происходит, куда нажать дальше и какой результат получен. Каждая видимая кнопка, ссылка, фильтр и настройка должна иметь реальный рабочий сценарий.

Не ограничивайся косметикой. Проверяй цепочку целиком: **экран → действие → API → PostgreSQL → повторное чтение → отображение результата**.

## Ограничения

- Не менять домен и HTTPS.
- Не включать реальные платежи: до отдельного решения сохранять `billing_mode=test_free` и цены `0 ₽`.
- Не удалять организации и данные без отдельного явного подтверждения пользователя.
- Сохранить канонический маршрут `/platform`, роли, tenant/venue-изоляцию и обратную совместимость с CRM.
- Не использовать пароль или PIN в отчётах, логах, скриншотах и коммитах.

## 1. Инвентаризация экрана

Составь таблицу всех элементов `/platform`:

- логотип и бренд;
- боковое меню;
- заголовок и статус платформы;
- KPI-карточки;
- список организаций;
- поиск;
- сортировка и фильтры;
- кнопка создания компании;
- форма onboarding;
- выбор тарифа;
- статус организации;
- кнопки открытия, редактирования, приостановки и возобновления;
- блок состояния платформы;
- настройки SaaS;
- выход;
- модальные окна, закрытие по Escape и клику вне окна.

Для каждого элемента зафиксируй: видимость, роль, состояние loading/empty/error/success, маршрут, HTTP-метод, API, права и сохранение.

## 2. Проверка кликабельности

Пройди все элементы вручную и автоматизированно:

- каждая ссылка ведёт в правильное место;
- якоря `#companies`, `#billing`, `#health`, `#settings` реально существуют;
- кнопки не являются декоративными `alert`-заглушками;
- повторный клик не создаёт дубликаты;
- Enter и Space работают для кнопок;
- Tab-порядок логичен;
- фокус видим;
- модальные окна имеют понятный возврат фокуса;
- действия недоступной роли скрыты или объясняют отказ.

## 3. Onboarding организации

Проверь полный сценарий:

1. SaaS-владелец нажимает «Добавить компанию».
2. Заполняет название, slug, город, адрес, тариф и владельца.
3. Сервер валидирует email, пароль, slug, timezone и тариф.
4. В одной транзакции создаются организация, подписка, первое заведение, владелец и membership.
5. При ошибке всё откатывается.
6. Новая компания появляется в списке без ручного обновления.
7. Владелец новой компании может войти и видит только свой tenant.
8. Повторная отправка формы не создаёт дубликат.

Проверь пустые поля, занятый slug, занятый email, слабый пароль, неправильный timezone, сетевую ошибку и повторную отправку.

## 4. Компании и подписки

Проверь для каждой организации:

- название, slug, город;
- число заведений и активных сотрудников;
- тариф и лимиты;
- статусы `trialing`, `active`, `past_due`, `cancelled`;
- смену тарифа;
- приостановку и возобновление;
- повторное чтение после обновления;
- аудит before/after, actor, organization и timestamp;
- поведение при превышении лимитов.

Тарифы должны иметь единый источник в API. UI не должен самостоятельно решать, разрешена ли операция.

## 5. Tenant isolation и роли

Создай минимум две тестовые организации и проверь прямыми API-запросами:

- организация A не читает организацию B;
- нельзя изменить тариф B через ID из URL без роли SaaS-владельца;
- владелец организации не получает `/api/platform/*`;
- SaaS-владелец не становится сотрудником tenant автоматически;
- `organization_id`, `venue_id` и scope из клиента не считаются доказательством доступа;
- все tenant-owned запросы получают контекст из проверенной сессии;
- архивная/приостановленная организация не может выполнять новые операции;
- фоновые задачи, кэш и файлы не пересекают tenant-границы.

## 6. Дизайн и понятность

Сделай интерфейс понятным человеку без технических знаний:

- один главный CTA над первым экраном;
- короткие названия меню: «Обзор», «Компании», «Состояние», «Настройки»;
- не использовать необъяснимые термины `Control Center`, `tenant`, `organization_id` в пользовательском интерфейсе;
- показать блок «С чего начать» из 3–5 шагов;
- понятные empty/loading/error/success состояния;
- рядом с тарифом показывать лимиты простыми словами;
- статус отображать текстом и цветом;
- опасные действия отделить и подтверждать;
- не использовать цвет как единственный способ передать статус;
- выдержать единые размеры, шрифт, отступы, иконки и фокус;
- проверить desktop, tablet, Fold и mobile без горизонтального скролла.

## 7. Проверка API и БД

Запусти:

- синтаксические проверки;
- route/API contracts;
- RBAC matrix;
- onboarding rollback;
- duplicate/race tests;
- tenant-isolation tests на двух организациях;
- quota tests;
- subscription lifecycle tests;
- audit tests;
- PostgreSQL migration upgrade/replay;
- браузерный обход `/platform` с авторизованной ролью `platform_owner`.

Для каждого найденного дефекта зафиксируй воспроизводимые шаги, первопричину и исправление. Не подменяй реальный API моками в production-сценарии.

## 8. Приёмка

SaaS считается готовым только если:

- нет декоративных или неработающих контролов;
- список организаций загружается и обновляется после действий;
- создание, изменение тарифа и статуса работают после reload;
- tenant isolation подтверждена отрицательными тестами;
- роли подтверждены сервером;
- ошибки понятны и восстанавливаемы;
- desktop/mobile/Fold проверены скриншотами;
- миграции повторяемы;
- `git diff --check` чистый;
- healthcheck после деплоя успешен;
- финальный отчёт содержит список проверенных элементов, API, тестов, скриншотов, commit SHA и оставшихся ограничений.

В финале раздели результат на: **готово**, **исправлено**, **проверено вручную**, **осталось до production billing/HTTPS**. Не заявляй PASS без фактического доказательства.
