# Безопасность перед боевым запуском

- Статический сервер отдаёт только явно разрешённые HTML/CSS/JS интерфейса, иконки и шрифты. Исходники сервера, `.env`, Git, SQL, архивы и зависимости закрыты даже для неавторизованного HTTP-запроса; символьные ссылки за пределы проекта также запрещены.
- `node scripts/local-static-boundary.mjs` проверяет этот запрет в отдельном временном процессе на loopback-адресе, доступность страниц и динамически подключаемых ресурсов, а также их включение в Dockerfile. Реальный Docker-образ проверяется отдельно перед развёртыванием.

- Не хранить пароли и PIN в репозитории; использовать Argon2id/bcrypt и секреты окружения.
- Новые пароли сотрудников хешируются через встроенный scrypt; legacy-значения из seed нужно заменить до боевого запуска.
- Сессии выдаются через HttpOnly/SameSite cookie с истечением 30 дней; bearer поддержан для API-клиента. На VPS с HTTPS включать `COOKIE_SECURE=true`, чтобы cookie передавалась только по TLS.
- Демонстрационные учётные записи доступны только без `DATABASE_URL`. При подключённой PostgreSQL вход проверяет пользователя и пароль в БД, сохраняет хеш сессии там же и отказывает при сбое записи. Перед VPS-релизом включить `AUTH_REQUIRED=true` и создать пользователей с индивидуальными паролями.
- Чувствительные API-маршруты проверяют роль и разрешение на сервере.
- Скидки, возвраты, оплаты, разделение заказа и списания требуют аудита.
- PostgreSQL не публиковать наружу; доступ только из внутренней Docker-сети.
- Nginx обслуживает HTTPS, ограничивает размер запросов и добавляет security headers.
- Регулярные резервные копии PostgreSQL и проверка восстановления.
- Интеграции ККТ/ЕГАИС/«Честный знак» включаются отдельными флагами и имеют очередь повторной доставки.
- Логи не должны содержать PIN, пароли, токены и полные платёжные реквизиты.
