# Рабочий процесс CRM

Командная модель из 16 ролей и порядок согласования закреплены в [`docs/AI_TEAM.md`](docs/AI_TEAM.md) и [`docs/AI_TEAM_WORKFLOW.md`](docs/AI_TEAM_WORKFLOW.md). Координацию активной задачи выполняет основной Codex по [`docs/AI_ORCHESTRATOR.md`](docs/AI_ORCHESTRATOR.md). Любой пакет изменений проходит этот workflow до коммита и публикации.

## Разработка и выпуск

Все обычные изменения сначала выполняются в текущем рабочем проекте локально. После каждой правки проверяются синтаксис, связанные сценарии и адаптивность, но Sites не создаётся и новая production-версия не сохраняется.

Изменения группируются по смыслу и выпускаются, когда достигнуты согласованные критерии приёмки. Фиксированного лимита правок, обязательного номера пакета или ожидания пятнадцати изменений нет. Каждый выпуск должен содержать совместимые изменения, прошедшие локальную проверку.

Перед публикацией проверяются:

- вход и выход для затронутых ролей;
- основные клики и сохранение данных;
- отсутствие горизонтального переполнения на мобильной ширине;
- `node --check`, `git diff --check` и релевантные smoke-проверки;
- соответствие архива опубликованному commit SHA.

## Учёт прогресса

Прогресс отмечается описанием результата, проверок и остаточных рисков в рабочем журнале. Счётчик вида `1/15` не используется как ограничение или условие выпуска.

## Исключения

Немедленная публикация допустима для исправлений, которые блокируют авторизацию, выход, оплату, сохранение критичных данных или устраняют уязвимость. Исправления документации и внутреннего кода можно отправить в репозиторий без отдельного production-развёртывания, если они не меняют сайт.

Новый сайт или новый проект Sites создаётся только по отдельному прямому запросу. Все остальные изменения продолжают текущий проект и его существующую production-аудиторию.
# Обязательное правило функциональной завершённости

Функция не считается реализованной, если существует только API, миграция, форма или кнопка. Перед сдачей необходимо подтвердить полный пользовательский путь:

`пункт меню → экран → действие → API → сохранение в БД → повторное отображение после обновления → использование связанным модулем`.

Для каждой новой сущности обязательно проверить создание, редактирование, архивирование/удаление, права ролей, пустую базу, ошибку и успешное подтверждение. Если сервер поддерживает действие, в интерфейсе должен существовать понятный путь к нему. Если интерфейс показывает действие, оно должно быть связано с рабочим API и проверено после перезагрузки.

Системный архитектор — владелец сквозной связки API и интерфейса. До реализации он фиксирует соответствие экранов и действий маршрутам/методам API, полям запроса и ответа, правам, состояниям загрузки/пустого результата/успеха/ошибки, сохранению и повторному отображению. Frontend и backend подтверждают свои части контракта, QA проверяет его на полном пользовательском сценарии. Несоответствие любого слоя блокирует приёмку функции.
