# API-контракт MVP

Базовый URL локально: `http://localhost:3000`.

## Служебные
- `GET /api/health` — состояние сервиса.
- `GET /api/products` — активные позиции меню для каталога.
- `GET /api/session?role=<role>` — демонстрационный профиль и разрешения роли.
- `GET/PATCH /api/session/preferences` — пользовательские настройки аккаунта (таймер блокировки, модули главной, вид выручки, показатели аналитики и вид каталога персонала); сервер валидирует допустимые значения и сохраняет их в PostgreSQL. `staffDirectory.view`: `cards` / `list` / `table`; `staffDirectory.cardScale`: целое число 1–4.
- `POST /api/session/unlock` — проверка 4-значного PIN для разблокировки рабочего экрана; после успешной проверки возвращает `ok`, текущий `token` и `user`.
- `POST /api/session/pin-return` — PIN-возврат на доверенном устройстве для `owner`/`admin`/`developer`; проверяет текущую cookie-сессию и PIN, возвращает `token`, `user`, `permissions`, `expiresIn` и `trustedDevice`.
- `GET /api/saas/account` — текущая организация, тариф, лимиты мест/заведений и активное использование (для владельца/администратора).
- `PATCH /api/staff/:id/pin` — сотрудник меняет свой 4-значный PIN; владелец/управляющий может выполнить операцию в рамках управления персоналом.
- `GET /api/notifications?limit=20&filter=all|unread` — доступные текущему пользователю уведомления (последние события), число непрочитанных и `hasMore`. Ответ не содержит сумм, строк заказа или PIN. Получатели: owner/admin с правами финансов и заказов для запросов скидки; owner/admin/manager с соответствующими правами склада или заказов; owner/admin с правом сотрудников для события смены PIN. Операционный сотрудник получает 403.
- `PUT /api/notifications/:id/read` — отметить доступное уведомление прочитанным. ID события повторно проверяется в активном заведении и по правам; чужой/недоступный ID возвращает 404.
- `POST /api/notifications` — отметить все доступные события прочитанными. Идентификатор пользователя и активное заведение берутся только из сессии; тело запроса не может менять область действия.

Состояние прочтения в PostgreSQL хранится отдельно по заведению, пользователю и стабильному ключу события (`notification_reads`, миграция `054_notification_reads.sql`). Demo/fallback без БД использует память процесса и не гарантирует сохранение после перезапуска. Ошибка источника возвращает 503, интерфейс показывает повтор загрузки. Открытие панели не отмечает уведомления прочитанными.

Открытие и закрытие смены также входят в уведомления: получатели — `owner/admin/manager` с правом `floor`, `orders` или `finance_read`. События активного заведения имеют стабильные ключи `shift_opened:<auditId>` / `shift_closed:<auditId>`; суммы кассы не включены в DTO. Колокольчик доступен этим руководителям и в рабочем зале. Прочтение индивидуально для пользователя и заведения. Это уведомления внутри CRM; отправка в Telegram не реализована этой функцией.

## Смены

- `GET /api/shifts` — `current` (активная смена либо `null`) и история `items`; нужны `floor`, `orders` или `finance_read`.
- `POST /api/shifts` — открыть смену с `openingCash`; нужны `floor` или `orders`. Повторное открытие активной смены возвращает 409.
- `POST /api/shifts/:id/close` — закрыть с `closingCash` и `checklistConfirmed: true`; нужны `floor` или `orders`. Повторное закрытие/чужая смена возвращает 404. Чек-лист подтверждает пользователь; это не автоматическая проверка завершения всех заказов.
- Денежные поля обязательны: число либо десятичная строка, от 0 до 100 000 000 включительно, не более двух знаков после точки. `null`, boolean, массивы, объекты и отрицательные значения отклоняются.
- В PostgreSQL изменение смены и событие `audit_events` сохраняются одной транзакцией. Ошибка записи аудита откатывает изменение смены. Конкурентные запросы не создают вторую активную смену/повторное закрытие.
- При настроенной, но недоступной БД возвращается 503 `shift_status_unavailable`; переключения на фиктивную локальную кассу нет.
- UI рабочего зала, главной и финансов перечитывает сохранённое состояние после действия, возврата в видимую вкладку и каждые 20 секунд в видимой вкладке. Показатели выбранного дня/смены обновляются при изменении состояния смены. Финансовая роль без управления видит статус без кнопки открытия/закрытия.
- `POST /api/login` — вход и выдача bearer-токена. Для `owner`/`admin`/`developer` поле `trustDevice: true` выдаёт долгую доверенную сессию, которая затем может быть восстановлена через PIN.
- `GET/PATCH /api/venue` — карточка компании, телефон, адрес и логотип.
- `GET/POST /api/staff`, `DELETE /api/staff/:id`, `POST /api/staff/:id/avatar` — управление сотрудниками и аватарами.
- `POST /api/staff/:id/archive` — владелец удаляет заранее заблокированного сотрудника из рабочего списка; кадровая и операционная история остаётся в аудите.
- `POST /api/products/:id/image` — загрузка изображения товара (PNG/JPG/WebP до 1.5 МБ).

## Планируемые маршруты
- `POST /api/auth/login` — вход по логину и паролю. PIN не участвует в авторизации и используется только для разблокировки экрана. Ответ содержит `user.organizationId` для tenant-контекста SaaS.
- `GET /api/floor?zone_id=` — зоны и столы со статусами.
- `GET /api/orders?status=open` — открытые заказы.
- `POST /api/orders` — открыть заказ на стол или свободный чек.
- `POST /api/orders/:id/items` — добавить позицию.
- `PATCH /api/orders/:id/items/:item_id` — изменить количество или станцию.
- `POST /api/orders/:id/split` — разделить позиции по гостям/новый заказ.
- `POST /api/orders/:id/discount-requests` — заявка только на процентную скидку (`type: "percent"`, `value: 1..100`, `reason`).
- `POST /api/clients/:id/loyalty` — ручная корректировка бонусного баланса с причиной и обязательным `idempotencyKey` (или заголовком `Idempotency-Key`); операция и баланс сохраняются атомарно в `guest_account_entries`, повтор возвращает результат прежней операции, списание сверх остатка отклоняется.
- `GET /api/clients/:id/account-entries` — журнал движений бонусного и денежного счёта гостя и текущие балансы; доступно финансовым/loyalty/staff-management ролям в рамках выбранной площадки.
- `POST /api/clients/:id/deposit-top-ups` — принять деньги на счёт гостя: `{amount,method:"cash"|"card"|"qr",reason,idempotencyKey}`. Требуется открытая смена и право orders или finance. Пополнение сохраняет отдельную квитанцию с кассиром и сменой и положительное движение обязательства; оно не создаёт продажу или платёж заказа. Наличные пополнения включены в ожидаемую наличность смены, карта/QR — нет. Повтор с тем же ключом и телом возвращает исходную квитанцию; иной payload под тем же ключом отвечает `409 idempotency_key_reused`.
- `PATCH /api/clients/:id` — профиль больше не меняет бонусный или денежный баланс. Изменение ненулевого остатка при создании гостя также отклоняется; баланс меняется через журналируемую операцию.
- `GET /api/discount-requests` — список заявок для финансовых ролей.
- `POST /api/discount-requests/:id/approve` или `/reject` — согласование или отклонение процентной скидки финансовой ролью.

На заказ допускается одна одобренная ручная скидка; повторное одобрение отвечает `409 approved_discount_exists`. При привязке гостя `PATCH /api/orders/:id` фиксирует текущую активную группу точки и её процент на заказе; `clientId: null` снимает привязку, но смена гостя после принятой оплаты отклоняется с `409 guest_change_after_payment`. Для legacy заказов общая скидка ограничивается стоимостью товаров. Групповая и ручная скидки не суммируются: берётся одна большая, при равенстве групповая. Оплата рассчитывается как `max(subtotal - selected_discount, vip_minimum)`, а VIP сводка показывает дефицит уже после скидки. `GET /api/orders/:id/summary` и `GET /api/orders/:id/payments` возвращают текущую цену и основание скидки; закрытый заказ новой версии отдаёт неизменный ценовой снимок.
- `POST /api/orders/:id/payments` — частичный или полный платёж способами `cash`, `card`, `qr`, `bonus` или `deposit`. Для бонусного тендера передаются `{method:"bonus",amount:<целое число>,idempotencyKey:<строка 8–120 символов>}`; один бонус равен одному рублю в этой временной локальной политике. Для денежного счёта передаются `{method:"deposit",amount:<положительная сумма>,idempotencyKey:<строка 8–120 символов>}`. Оба списания требуют привязанного гостя, не могут превысить баланс/долг и атомарно создают отдельный тендер и отрицательное движение журнала. Повтор с тем же ключом и телом возвращает исходный платёж; тот же ключ с другим телом отвечает `409 idempotency_key_reused`. Ответ и GET содержат актуальный `guestAccount`. Оба тендера учитываются в смене как безналичный `other`, но не увеличивают наличность. При полном закрытии заказа обработчик атомарно начисляет целое число бонусов по `bonus_percent` активной группы гостя. `POST /api/orders/:id/close` делает то же самое. База начисления — стоимость товаров после скидки, но до доплаты до VIP-минимума; также из базы исключены потраченные при оплате бонусы, но не денежный счёт; дробные бонусы округляются вниз. Ответ закрывающего запроса включает снимок процента/базы/начисления и новый бонусный остаток. Частичная оплата начисление не запускает; `GET /api/orders/:id/payments` возвращает сохранённый снимок условий начисления.
- `POST /api/reservations` — создаёт бронь; поле `deposit` — требуемая сумма, а не принятое поступление. Новые брони сохраняют `deposit_required=deposit` и `deposit_paid=0`.
- `POST /api/reservations/:id/deposit-receipts` — принимает частичную/полную предоплату `{amount,method:"cash"|"card"|"qr",reason,idempotencyKey}`. Нужны право `reservations`, подтверждённая бронь и открытая смена; сумма ограничена `deposit_required - verified_deposit_paid`. Переплата, отменённая бронь и неразобранный старый `deposit_paid` отклоняются. Квитанция записывает площадку, бронь, смену, сотрудника и время; квитанция, остаток и аудит сохраняются транзакционно. Точный повтор возвращает прежнюю квитанцию, повтор ключа с изменённым телом — `409 idempotency_key_reused`.
- `POST /api/orders` принимает необязательный `reservationId` для начала визита из подтверждённой брони. Пользователь должен иметь права `orders` и `reservations`; бронь, стол и гость проверяются в текущем заведении. Одна бронь может быть связана только с одним заказом.
- Для связанного с бронью заказа `GET /api/orders/:id/payments` дополнительно требует право `reservations`, поскольку возвращает квитанции и доступные остатки.
- `POST /api/orders/:id/payments` принимает `{amount,method:"reservation",receiptId,idempotencyKey}` для зачёта выбранной квитанции в связанный заказ; требуются права `orders` и `reservations`. Распределение, payment tender и аудит атомарны. Исходная receipt не переписывается; тендер не добавляет наличность второй раз, а выручка учитывается только как часть закрываемого заказа. Отменить бронь с уже применённой суммой нельзя; возврат остаётся отдельным будущим действием.
- `GET /api/reservations` и `GET /api/clients/:id/history` возвращают `depositRequired`, квитанционно подтверждённый `verifiedDepositPaid`, `prepaymentReceipts` и старую неподтверждённую `legacyDepositPaid` отдельно. Историю не переписываем; суммы без квитанции требуют сверки.
- `GET /api/dashboard/shift-kpis` показывает `totals.reservationPrepayments` (`total`, `cash`, `cashless`, `count`) отдельно от выручки и платежей заказов. Наличные предоплаты включены в ожидаемую наличность смены; карта/QR исключены из кассовой наличности. Отмена сохраняет квитанции и не запускает автоматический возврат.
- `GET /api/inventory` — остатки и предупреждения.
- `GET /api/inventory/premixes` — до 100 последних партий: плановый и фактический выход, остаток партии, срок годности, исполнитель и себестоимость. Для партий, созданных до lot tracking, остаток остаётся в нераспределённом legacy остатке.
- `POST /api/inventory/premixes/produce` — выпуск партии; `actualOutput` необязателен и задаётся в единице техкарты, `expiresAt` необязателен и задаётся ISO timestamp.
- `POST /api/inventory/premixes/{batchId}/waste` — списать `quantity` из конкретной партии с обязательной причиной `reason`.
- `POST /api/inventory/premixes/{batchId}/count` — сверить партию с фактическим `actualQuantity`; корректировка сохраняется отдельным складским движением.
- `POST /api/inventory/premixes/{batchId}/void` — отменить выпуск только до дальнейших движений по позиции и без списаний партии; `reason` рекомендуется указать. Исходные записи сохраняются, сырьё возвращается складскими движениями.
- `POST /api/audit/events` — внутренний журнал действий.

Каждый изменяющий запрос должен передавать идентификатор сотрудника и создавать событие аудита. Проверка прав выполняется на сервере, а не только скрытием кнопок в браузере.

- POST /api/orders/:id/split — перенос выбранных позиций в новый заказ.

- GET /api/floor — зоны и статусы столов для рабочего экрана.

- GET /api/staff — список сотрудников; POST /api/staff — создание сотрудника с ролью.

### POST /api/orders/:id/close
Закрывает заказ. Для VIP возвращает subtotal, finalTotal и minimumAdjustment; итог не может быть ниже minimumOrderTotal.


- GET /api/venue — профиль площадки и минимумы VIP-комнат.
- GET /api/integrations — состояние интеграции Telegram.

- `/api/finance/summary`, `/api/finance/report`, `/api/analytics` для рядового сотрудника возвращают только его оборот за текущий бизнес-день; период и дата из запроса не расширяют доступ.
- GET /api/metrics — агрегаты для административного обзора.
- GET /api/audit — последние события аудита действий пользователей.
- GET /api/orders?venueId=… — использует PostgreSQL-репозиторий при настроенном DATABASE_URL.
- При `DATABASE_URL` список открытых заказов читает PostgreSQL-репозиторий `db.js`; без переменной используется demo-режим.

### SaaS Control Center
- GET /api/platform/overview — агрегаты организаций, только platform_owner.
- GET /api/platform/organizations — реестр компаний и тарифов, только platform_owner.
- POST /api/platform/organizations — создание организации, первого заведения, trial-подписки и учётной записи владельца (`ownerName`, `ownerLogin`, `ownerPassword`), только platform_owner.

- GET /api/platform/plans — тестовый каталог тарифов, все цены 0 ₽.
- GET/PATCH /api/platform/organizations/:id/subscription — просмотр и переключение тарифа без списаний.
- Лимиты подписки проверяются на сервере при создании сотрудников и заведений: при исчерпании API возвращает `409 seat_limit_reached` или `409 venue_limit_reached` с `limit` и `used`. Сотрудник сохраняется с `organization_id` и активным членством.
- При отменённой подписке, отключённой организации или неактивном членстве tenant-вход и запросы текущей сессии отклоняются с `403`; состояние `past_due` пока сохраняет доступ.


## Справочники склада: архив и удаление

- `GET /api/inventory/departments?status=active|archived|all`, `GET /api/inventory/subdepartments?status=active|archived|all` и `GET /api/product-categories?status=active|archived|all`; без `status` возвращаются только активные записи. Чтение требует `inventory_read`; каждый ответ ограничен текущим заведением.
- `DELETE /api/inventory/departments/:code`, `/api/inventory/subdepartments/:id` и `/api/product-categories/:id` — только обратимый архив, требуется `inventory`. Архивируются только записи без текущих ссылок; данные и история не удаляются.
- `POST .../:id/restore` восстанавливает запись при активном родительском цехе и без конфликта уникальности.
- `POST /api/inventory/permanent-deletions` выполняет окончательное удаление архивной записи только для `owner`; сервер блокирует удаление при наличии подцехов, категорий, позиций или товарных ссылок. Если владелец удалил запись напрямую, ожидающий запрос управляющего закрывается в той же транзакции.
- `POST /api/inventory/deletion-requests` создаёт запрос управляющего на удаление архивной записи; `GET /api/inventory/deletion-requests` показывает владельцу ожидающие запросы, управляющему — только собственные. `POST /api/inventory/deletion-requests/:id/approve|reject` доступен только роли `owner`. Подтверждение повторно проверяет ссылки и выполняется в одной транзакции с решением запроса.

## Технологические карты

- `GET /api/recipes` возвращает активные карты, включая текстовую категорию `category`.
- `POST /api/recipes` и `PATCH /api/recipes/:id` принимают необязательную категорию длиной до 80 символов. Категории можно вводить свободно; интерфейс предлагает уже созданные.
- Поиск в списке технологических карт выполняется по названию, категории, связанному товару, ингредиентам, приготовлению и подаче. Фильтр категории строится по сохранённым картам и не меняет их состав или привязки.
