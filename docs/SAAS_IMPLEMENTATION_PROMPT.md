# Рабочий промт: завершение SaaS-режима Hookah POS

Ты работаешь над SaaS-режимом Hookah POS / Territory Cloud. Цель — довести мультитенантный контур до проверяемого beta-ready состояния без домена и HTTPS: общий сервер и код, изолированные организации, несколько заведений, роли и пробные тарифы.

## Архитектурные правила

1. Tenant-контекст берётся только из серверно проверенной сессии и membership. `organization_id`, `venue_id` и scope из URL, query, body или заголовка являются только селекторами и никогда не доказательством доступа.
2. Каждый tenant-owned запрос обязан проверять принадлежность ресурса текущей организации и активной точки. Запросы платформенного владельца явно отделены от клиентского tenant-контекста.
3. Применяй defense in depth: проверка в middleware/API, составные ограничения и индексы БД, по возможности PostgreSQL RLS или отдельные DB-роли для чувствительных контуров.
4. Не смешивай глобальные справочники платформы, данные организации, данные заведения и данные пользователя. Кэш, файлы, очереди и фоновые задачи должны содержать проверенный tenant-контекст.
5. RBAC проверяется на сервере. UI только скрывает недоступные действия и не является защитой.
6. Onboarding организации выполняется атомарно: организация, подписка, первое заведение, владелец и membership создаются одной транзакцией. Ошибка откатывает всё.
7. Offboarding не удаляет историю молча: приостановка блокирует новый вход и операции, а архивирование и удаление требуют отдельного аудируемого сценария.
8. Лимиты тарифа проверяются сервером при создании пользователя, заведения и платного модуля. Ошибка должна быть понятной и не раскрывать чужие данные.
9. Статусы подписки: `trialing`, `active`, `past_due`, `cancelled`. Пока биллинг тестовый, цены равны нулю, но переходы и аудит должны быть совместимы с будущим провайдером платежей.
10. Любое изменение тарифа, статуса, лимитов, владельца или membership записывается в audit log с actor, organization, resource, before/after и request id.

## Обязательные пользовательские пути

- platform owner: вход → обзор → список организаций → поиск → создание организации → повторный вход владельцем созданной организации;
- platform owner: смена тарифа и статуса → повторное чтение после обновления → проверка лимитов;
- tenant owner: вход → выбор заведения → работа только со своими данными;
- tenant admin/member: проверка разрешённых и запрещённых API действий;
- две организации: одинаковые URL/id-селектора не дают cross-tenant чтение, изменение или удаление;
- paused/cancelled организация: новые операции отклоняются, аудит сохраняется;
- reload/restart PostgreSQL: данные и membership сохраняются.

## Проверки перед завершением

Запусти миграции с upgrade/replay, API contract tests, RBAC matrix, tenant-isolation tests с двумя организациями, onboarding/rollback, quota tests, audit tests, responsive проверки desktop/mobile/Fold и браузерный обход. Для каждого исправления покажи UI → API → БД → повторное отображение. Не утверждай готовность по одному зелёному smoke-тесту.

## Ограничения проекта

Сохрани канонические маршруты, tenant/role/venue совместимость и существующие demo-данные. Не публикуй production, не включай реальный биллинг и не меняй домен/HTTPS без отдельного запроса. Синхронизируй `dist`, документацию, контракты и журнал работы. В финале укажи, что доказано тестами, что проверено вручную и что остаётся до production SaaS.
